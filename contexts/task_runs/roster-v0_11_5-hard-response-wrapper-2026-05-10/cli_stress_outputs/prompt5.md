這輪先停在判斷，不建 packet、不改文件、不寫正式 review。

我會先把問題分成幾個層次看：

1. **資源契約層**
   資料、圖片、圖表、版型到底誰是 source of truth？有沒有 asset manifest、版本、路徑、授權、尺寸、格式要求？如果只是靠 prompt 或檔名串起來，整合通常會不穩。

2. **中介規格層**
   有沒有一份明確的 slide spec / deck spec，描述每張投影片要用哪些資料欄位、圖表、圖片、版面 slot？如果沒有，流程可能「能產出」，但每次都靠模型或腳本猜。

3. **轉換層**
   圖片、SVG、PNG、HTML、PPT native shape、chart/table 之間的轉換邊界可能混亂。特別要分清楚：哪些應該是可編輯 PowerPoint 物件，哪些只是高解析透明 PNG 視覺板。

4. **版面組合層**
   常見問題是圖片裁切、文字溢出、圖表縮放、z-index、placeholder 對不上、長標題壓壞 layout。這不是「美觀」問題，而是 resource binding 和 layout constraint 沒有被驗證。

5. **驗收證據層**
   若目前只檢查「檔案有產生」「指令成功」，那不足以證明簡報可交付。簡報流程至少要有 render/export 後的視覺證據，並能對照 source assets。

6. **流程控制層**
   需要看是否有 stale cache、重跑不可重現、失敗被 fallback 靜默吞掉、asset output path 固定但未清理、上一輪圖片誤用到下一輪等問題。

下一輪我建議先看這些證據，順序如下：

1. 一次實際流程的輸入：資料檔、圖片/圖表來源、簡報目標說明、模板。
2. 流程中間產物：deck spec、asset manifest、生成的圖表檔、轉換後圖片、log。
3. 最終輸出：PPTX / PDF / PNG render，最好有每頁截圖。
4. 任一頁出錯案例：指出「哪張投影片、哪個資源、哪種不穩」，例如資料沒進去、圖片錯位、圖表不一致、版面壓壞。
5. 產出腳本或 prompt chain：看它是靠明確 binding，還是靠自然語言和檔名推斷。

核心判斷標準是：**能不能從最終投影片追溯回每個資料、圖片、圖表和版面 slot 的來源與轉換步驟**。如果追不回去，問題大概率在資源整合流程，而不只是某次生成品質差。
