本次啟用：4 個 role-agents  
目前階段：初步規劃；正式 artifact 這輪先不產出。

我會先把這題判斷成三個真正影響 sprint 決策的問題：

1. 新使用者不知道第一步：是否直接卡住 onboarding / activation？
2. 通知太多：是否讓重要交付訊號被淹沒？
3. 主管只想看本週交付風險：是否缺少可行動的摘要，而不是缺少更多通知？

**優先順序判斷**

| 判斷面向 | 優先處理訊號 |
|---|---|
| 影響 onboarding | 新帳號登入後沒有完成第一個關鍵動作、第一次成功操作時間過長、重複問「下一步要做什麼」 |
| 影響交付 | 因通知漏看造成 approval 延遲、任務卡住、交接失敗、本週到期事項無 owner |
| 重複發生 | 客服、CS、產品回饋反覆出現同一類問題 |
| 兩週可改 | 文案、空狀態、預設通知、摘要規則、簡單儀表板區塊可處理；大流程重構先不排 |
| 證據可信 | 有 funnel、ticket、session replay、內部交付紀錄互相支持，而不只是單一抱怨 |

**要收集的證據**

- onboarding funnel：註冊、首次登入、第一個關鍵動作、完成 setup 的比例與耗時。
- 新手行為證據：空狀態停留、重複點擊、離開頁面、help / docs 點擊。
- 客服與 CS 回饋：近 2-4 週 ticket 分類，尤其是「不知道下一步」「通知太多」「漏掉重要事項」。
- 通知資料：每人每日通知量、開啟率、點擊率、mute / ignore、真正需要行動的通知比例。
- 交付影響證據：本週延遲、blocked task、未回覆 approval、missed handoff 是否和通知或 onboarding 混亂有關。
- 工程估算：每個候選改善是否能在兩週內完成、是否牽涉資料模型、權限、通知規則引擎或跨團隊 dependency。

**兩週內最可能先處理**

第一優先會是「新手第一步」：在後台首頁或空狀態加明確的 primary action、setup checklist、下一步提示。這通常比重做整個 onboarding 流程便宜，且最容易直接改善 activation。

第二優先是「通知降噪」：先把通知分成 `需要行動`、`狀態更新`、`FYI`，調整預設頻率或做 digest。兩週內不建議做完整通知規則引擎，先處理最吵、最低價值的通知類型。

第三優先是「主管本週交付摘要」：先做一個簡化版週摘要邏輯，列出本週到期、無 owner、卡住超過一定天數、等待 approval 的事項。重點是讓主管少看通知，多看風險。

本次分工執行：產品視角負責判斷 activation 與新手第一步；資料視角負責定義 funnel 和通知指標；客服/CS 視角負責整理重複問題；交付視角負責把問題轉成「本週是否影響交付」的判斷。

最後收斂：這輪先不寫提案。下一步最實際是先整理一份候選問題清單，每個問題只填四欄：`證據`、`影響 onboarding/交付`、`兩週可行性`、`建議排不排進 sprint`。
